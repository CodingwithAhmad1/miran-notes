# Block chrome interaction model (design)

## Goals

- Preserve a **single** `NSTextView` typing surface while allowing **future** interactive gutters (drag handles, per-block actions) without rewriting the `EditCommandEngine` contract.

## Current implementation

- [`BlockChromeOverlayView`](../../Sources/MiranNotesApp/Features/Editor/BlockChromeOverlayView.swift) is **non-interactive** (`hitTest` returns `nil`). It draws hover and caret block gutters using `NSLayoutManager` geometry.
- Block identity comes from `Block.id` and UTF-16 `TextRange` in `NoteDocument.metadata.blocks`.

## Future interactive chrome (hooks)

1. **Hit testing** — Introduce a narrow protocol mapping view coordinates → `blockID` using the same `DocumentLayoutController.blockIndex` logic as context menus. A placeholder [`BlockChromeInteraction`](../../Sources/MiranNotesCore/BlockChromeHooks.swift) protocol exists in core for future extension modules.
2. **Commands** — Drag-and-drop reorder maps to a **sequence** of `EditCommand`s (cut range, paste at boundary) generated by a dedicated helper, not ad hoc text edits.
3. **Invalidation** — Chrome layout must follow `NSTextView` frame/bounds notifications (already observed for passive overlay).

## Non-goals (short term)

- Per-block `NSTextView` instances or virtualized block views — incompatible with the current single-surface reconciliation model without a full editor rewrite.
